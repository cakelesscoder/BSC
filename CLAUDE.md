# Notes for Claude Code

This is the source for the Orion Base System Configurator. Read README.md first for the overall layout.

## Don't edit `index.html` directly

`index.html` is generated by `build.py`. Edit `src/template.html` for code/layout/style changes, or the `data/*.json` files for content changes, then run `python3 build.py`.

If the user asks for a change and you find yourself reaching for `index.html`, stop and edit the appropriate source file instead.

## Where things live

- **Visual / layout / behaviour** → `src/template.html`. Single file, embedded CSS, embedded JS, no framework. The `DATA` constant inside the script is a placeholder — it gets replaced at build time. Don't put real data there.
- **Wording the customer reads** → `data/blurbs.json` (one-line option taglines) and `data/help.json` ("More info" panel text). These are hand-curated; the user will re-write them as they refine the product copy.
- **Option labels** → `data/options.json` (just the noun-phrase, e.g. "Mild Steel", "Gas Cooled"). Keep these short — the blurb carries the descriptive copy.
- **Question titles and subtitles** → `data/questions.json`.
- **Display order of options** → `data/option_order.json`. The order here is what the user sees; alphabetical-by-code is the fallback when the array is missing.
- **Compatibility rules** → `data/rules.json`. This is auto-generated and large. **Don't hand-edit it** unless you're fixing a single rule — the right way to refresh it is by re-running `scripts/extract_from_xlsx.py` against a new spreadsheet.
- **Images** → `images/NN-name/` folders (e.g. `01-process/`, `02-material/`). Folder names are prefixed with the question number and match the `folder` field in `questions.json`. Run `python3 scripts/index_images.py` after adding/removing images, then rebuild.
- **Development journal** → `docs/dev-journal/` contains design decision records for this project.

## The configurator

13 steps (was 14 — Jigs/Q11 removed due to poor spreadsheet data; can be re-added when proper source data is available). The steps are: Process, Material, Reach, Power, Cooling, Conduit, Fume, Wire, Touch Sensing, Tables, Guarding, Installation, Training.

## Compact config code

The summary screen generates a compact 17-character code like `MC3-5GS-NRY-2-4OO`. Each question maps to a single mnemonic character, grouped by logical section with hyphens. The `CODE_MAP` constant in the template defines the mapping. This code is the handoff format — customers send it to Orion, where a future internal tool will decode it into a costed proposal.

Format: `{Process}{Material}{Reach}-{Power}{Cooling}{Conduit}-{Fume}{Wire}{Touch}-{Tables}-{Guard}{Install}{Training}`

See `docs/dev-journal/001-compact-code-and-summary-redesign.md` for the full character table.

## The rule engine

Each rule is `[option_code, [prereq_for_q1, prereq_for_q2, ..., prereq_for_q_n_minus_1]]` where each prereq is a 3-digit code OR `null` (wildcard). An option is valid for the current selection chain if at least one of its rules has the property: every non-null prereq position equals the user's selection at that position.

The matcher (`getValidOptions` in the template) has two fallbacks:
1. If the question's rule set doesn't enumerate all options (i.e. some options have zero rules), the question is treated as fully permissive — show everything. This is because the source spreadsheet ships with rules for guarding/install/training only enumerated for one option each.
2. If rules exist for all options but the current chain doesn't match any rule (sparse-coverage gap), fall back to showing all options. Better to let a user pick a not-strictly-validated combination than to dead-end them.

When debugging "why is this option disabled" or "why is this option unexpectedly available", reproduce the user's chain in `state.selections` and trace through `getValidOptions` mentally — both fallbacks above mean the matcher can be permissive in ways that aren't obvious from the rules alone.

**Known quirk:** Wire rules have 6 prereqs instead of 7 (missing the fume position). This is a pre-existing spreadsheet issue — the `and_cols` for wire only has 6 entries. The rule engine handles short prereq arrays gracefully.

## Spreadsheet quirks already handled

- Option label `343` for Drum Pack is a typo in the spreadsheet — the rules use `453`. The extractor remaps via `CODE_REMAP` in `extract_from_xlsx.py`. If a future version fixes the typo at source, the remap becomes a no-op and is safe to leave in place.
- "parallet" → "parallel" and "Extration" → "Extraction" typo fixes live in `LABEL_FIXES` in the same file.
- Pandas `NaN` from empty spreadsheet cells was being concatenated into labels (e.g. "5 x Jig Table Frame nan"). The extractor now filters `nan` strings.

If you find more, add them there rather than hand-editing `data/options.json` — a future re-extract would otherwise overwrite the fixes.

## What I tried and rejected

- **Embedding images as base64** in a single self-contained HTML — file would be ~30 MB. Not friendly for GitHub Pages or iframe loading.
- **Strict rule matching with no fallback** — caused dead-ends because the spreadsheet's rules are sparse. The current permissive-fallback approach is what the user wants.
- **Hiding disabled options entirely** — losing the educational value of "you can't have water cooled with 350A" was worse than the cost of a bit more visual noise. Disabled options stay visible with a "NOT AVAILABLE" badge and a tooltip.
- **Interactive carousel buttons inside option cards** — nested `<button>` elements inside the option `<button>` broke click-to-select. Replaced with a hover slideshow (images auto-crossfade on hover) and a "N photos" badge that opens the lightbox.

## Testing

There are no automated tests in this bundle. The minimum smoke test before shipping a change:

```bash
python3 build.py
python3 -m http.server 8000   # in one terminal
# In a browser: visit http://localhost:8000, walk through all 13 steps,
# verify the compact config code looks right and copy/email/print all work.
```

If you're using Playwright for headless verification:

```python
page.click('#start-btn')
for _ in range(13):
    page.locator('button.option:not([disabled])').first.click()
    page.click('#next-btn')
# Then assert that page.locator('#config-code') is non-empty and matches /[A-Z0-9]{3}-[A-Z0-9]{3}-[A-Z0-9]{3}-[0-9]-[A-Z0-9]{3}/
```

## Useful patterns when extending

- **Adding a step that's purely informational** (no choice to make) doesn't fit the current model — every question has options. If you need an info-only step, render it inside `renderWelcome()` or as an extra summary block, not as a question.
- **Lightbox** — the `#lightbox` element is wired up with prev/next/keyboard/close. It's triggered by clicking the "N photos" badge on option cards. To add lightbox support to new elements, call `openLightbox(qkey, imgsArray)`.
- **Persisting selections** — currently in-memory only; closing the tab loses everything. If asked, use `sessionStorage` (not `localStorage`) keyed by something stable. Don't add a server.
- **Re-adding Jigs (Q11)** — if the spreadsheet data is cleaned up, add it back to `questions.json`, `options.json`, `blurbs.json`, `help.json`, `option_order.json`, and re-extract rules. Also add it back to `CODE_MAP`, `SPEC_GROUPS`, and both `selOrder` arrays in the template. Create an `images/11-jigs/` folder.

## Domain context

Read the user's memory entries for what they actually do — they work in welding automation, sell Panasonic robot welding systems through Orion Automation Systems in Australia/NZ. The configurator is for their own customers (fabricators) to spec a cell before contacting Orion for a quote. The audience is technical (welding shop foremen, engineering managers) — they already know their materials and processes. Don't explain what mild steel is for.

When writing copy, lean into specifics: "1437 mm reach, 6 kg payload" beats "compact and capable". Avoid sales adjectives. The user wrote about caring for "real robots, real experience, real speed" on their site — that's the tone.

**Do not invent specifications you don't know are correct** — the existing blurbs include some specific numbers (reaches, payloads, duty cycles) that were Claude's best guesses from general Panasonic robot knowledge. The user has flagged that they need to be reviewed. If you're refining wording, ask before you confidently state numerical specs.
